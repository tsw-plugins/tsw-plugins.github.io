# 01 — Source comparison: UE4SS vs UEVR as the loader base

Both projects were cloned and inspected on 2026-10-17:

| | RE-UE4SS | UEVR |
| --- | --- | --- |
| Repo | github.com/UE4SS-RE/RE-UE4SS @ `1ba38db` (2026-10-14) | github.com/praydog/UEVR @ `4ee5c6b` (2026-08-29) |
| License | **MIT** (whole tree) | **"All rights reserved"** for the framework. Only `include/uevr/API.h`, `API.hpp` and `Plugin.hpp` (the plugin-facing API) are MIT. |
| Stated UE range | 4.7 – 5.8 | 4.8 – 5.4 |
| Language / build | C++23, CMake + Ninja/VS 2022, MASM | C++23, cmkr (CMake TOML), VS 2022, MSVC only |

| Injection | Proxy DLL (`dwmapi.dll` by default, generated by `proxy_generator`; other names possible, e.g. `user32.dll`), loads at process start | External injector (`UEVRInjector.exe`, .NET 6) after the game is running; `DllMain` entry |
| Engine discovery | Rust `patternsleuth` AOB scanner + per-game signature overrides (`UE4SS_Signatures/*.lua`) + `[EngineVersionOverride]` + member-variable layout templates for 4.14 … 5.x | `kananlib` + `sdkgenny` + `bddisasm` scanning; UESDK for layouts |

## What UEVR does better

- **Hook core.** safetyhook/asmjit is a cleaner, faster mid-function hooking
  stack than PolyHook 2, and UEVR's `Framework` has mature D3D/XInput/window
  message hooking.
- **Engine tick callbacks.** `on_pre_engine_tick` / `on_post_engine_tick`
  with the `UGameEngine*` and delta time are exactly the cadence a netcode
  layer wants. UE4SS's `on_update` is equivalent in practice (it runs on the
  game thread each frame) but less explicit.
- **Plugin ABI stability.** The C API in `API.h` is versioned
  (`2.39.0`) and ANSI-C; UE4SS's C++ mod ABI tracks the UE4SS build.

## What UE4SS does better, and why it wins

1. **License.** MIT vs. all-rights-reserved. A community project cannot fork
   or redistribute UEVR's framework source.
2. **Buildability.** UEVR's UESDK needs Epic org membership for every
   contributor. UE4SS builds from public sources.
3. **Already proven on TSW.** Signatures found, a custom fork exists, mods
   ship on it, and modders have dumped TSW's Lua types with it.
4. **Reflection-level function hooks.** `RegisterHook` on a specific
   `UFunction` (e.g. `/Script/TS2Prototype.VirtualHIDComponent:InputValueChanged`)
   is what the control-sync and spawn-interception layers need. UEVR gives a
   single global `ProcessEvent` hook, which is heavier and coarser.
5. **Dumpers.** UHT/C++ header dumps and Lua type generation turn TSW's
   `TS2Prototype` module into browsable headers, which is most of the
   reverse-engineering work.
6. **Lua for iteration.** Prototyping ghost-actor spawning in hot-reloaded
   Lua is far faster than rebuilding a DLL per attempt.

## Recommendation

Use **UE4SS as the loader**, unmodified where possible:

- Vendor upstream `RE-UE4SS` as a git submodule (as `TSW5Mods` and
  `tsw-controller-app` already do), **not** the stale `RE-UE4SS-TSW` fork
  (April 2025 base, pre-CMake, xmake era). Carry a TSW custom game config
  (`UE4SS-settings.ini` + any signature overrides) in this repo instead.
- Ship `tsw-coop` as a **C++ mod** (`CppUserModBase`) for the hot path
  (actor sync every tick, networking thread, interpolation) and a
  **Lua companion** for experiments and debug commands.
- Borrow from UEVR only what is MIT: the *idea* of a versioned C plugin API
  for third parties, and the engine-tick callback shape. If a better hooking
  core is ever needed, pull `safetyhook` directly (it is its own MIT
  project), not UEVR.

## Things that neither project provides

- Any networking. Both are strictly local.
- Actor replication. TSW is a single-player build; `AActor::bReplicates`,
  `NetDriver` and the rest of UE's networking are compiled in but unused and
  must be assumed broken for this game. The co-op layer has to carry its own
  transport and its own notion of "remote actor" (see 03-architecture).
- Knowledge of TSW's own classes (`ARailVehicle`, SimuGraph, dispatcher).
  That comes from dumps and from the prior art in the next document.
